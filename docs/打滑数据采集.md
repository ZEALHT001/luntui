# 打滑数据采集

## 双通道

- `VMCVOFA`：默认 20 ms，记录完整控制状态、状态机、关节负载和超时信息。
- `VMCFAST`：默认关闭，采集时启用 4 ms，高速记录原始轮速、轮反馈力矩、轮输出电流、IMU 纵向加速度、腿长和 phi0 状态。负载是**二进制定长帧**，不是 ASCII 文本。

`VMCFAST` 不经过打滑门控，也不会因打滑 latch 修改数据。固件仍会计算现有滑移指标，`slip_left`、`slip_right` 记录的是原始 latch；只有显式设置 `slip_enable=1` 时，latch 才会改变卡尔曼轮速输入。

## 传输格式与带宽

| 流 | 编码 | 帧长 | 频率 | 带宽 |
| --- | --- | ---: | ---: | ---: |
| `VMCVOFA` | ASCII 文本行 | ~1088 B | 50 Hz | ~54.4 kB/s |
| `VMCFAST` | 二进制定长帧 | 90 B | 225 Hz | 20.3 kB/s |
| 合计 | | | | **~74.7 kB/s** |

`VMCFAST` 的发射门用 1 ms 的 HAL tick 计时，而控制环固定为 2222 µs（450 Hz）。4 ms 的门只能落在 2 个控制周期（4444 µs）上，所以高频流实际是 225 Hz 而不是请求的 250 Hz。这是均匀降频，不是丢帧，帧间隔稳定在 4/5 ms 交替。要精确 250 Hz 需要把控制环改成 4 ms 的整数分之一，那会改变整定基准，因此保持现状。

之前 `VMCFAST` 是 43 字段的 ASCII 文本，帧长 277 B，双通道合计 113 kB/s，64 KiB RTT 上行缓冲只能覆盖 0.58 s。改成二进制并扩到 128 KiB 后，余量约 2.0 s。

`VMCFAST` 帧结构（小端，定长 90 B）：

| 偏移 | 长度 | 内容 |
| ---: | ---: | --- |
| 0 | 2 | 同步字 `0xFA 0xCE` |
| 2 | 1 | 版本号（当前 1） |
| 3 | 1 | 帧总长（90） |
| 4 | 4 | `seq` 帧序号，单调自增 |
| 8 | 4 | `t_ms` HAL tick |
| 12 | 4 | `loop_count` 控制环计数 |
| 16 | 2 | `loop_dt_us` 实测控制周期 |
| 18 | 10 | 状态标志字节 |
| 28 | 60 | 30 个 int16 定点标量 |
| 88 | 2 | CRC-16/CCITT |

`seq` 是用来区分丢帧来源的：`seq` 连续而到达有缺口，说明帧已经写进 RTT 缓冲、主机没读到；`seq` 本身跳号，说明固件就没写出去。

标量的定点比例写在 `VMC_LQR_RTT_FAST_SCALARS` 里，`tools/slip_capture.py` 有一份镜像表，`tools/test_slip_capture.py` 会在两份表不一致时失败。采集脚本输出的 CSV 列名和数值单位与之前完全一致（电流是裸值，其余按比例还原成物理量），分析流程不用改。

## 采集模式

链路异常时需要区分是单路本身有问题，还是两路叠加导致的，因此提供三种模式：

```sh
python3 tools/slip_capture.py --duration 10 --mode slow   # 只收 VMCVOFA 50 Hz
python3 tools/slip_capture.py --duration 10 --mode fast   # 只收 VMCFAST 250 Hz
python3 tools/slip_capture.py --duration 10 --mode both   # 两路同时
```

- `slow`：完全关闭 `VMCFAST`，是真正的单通道低频。
- `fast`：只记录 `VMCFAST`；`VMCVOFA` 被压到固件允许的最低速率 5 Hz（固件没有单独的关闭开关，不重新烧录无法完全停发）。
- `both`：默认模式，行为与之前一致。

判定链路是否可用要看 `coverage_pct`，不要看旧的 `missing_frames_pct` 语义。一次 4 秒停顿在旧统计里可能只显示零点几个百分点，但真实覆盖率只有约 40%。

## 控制环周期

控制环固定在 **2222 µs（450 Hz）**，见 `VMC_CONTROL_PERIOD_US`。此前它是自由运行的，格式化开销一变化频率就跟着变——去掉 `snprintf` 后曾一度升到 750 Hz。控制器里所有速率项都乘实测 `dt`，理论上频率变化不改变整定，但每个滤波器的离散实现会变，而这台车是按 450 Hz 整定的，所以周期现在被钉死，遥测或格式改动不会再影响闭环响应。

FreeRTOS tick 是 1 ms，因此剩下的亚毫秒余量靠在 TIM1（1 MHz）上轮询等待。实测 `loop_dt_us` 中位数 2222、范围 2207–2236 µs。板子上没有看门狗也没有空闲钩子，控制任务忙等是安全的。

## 采集路径

默认走 `gdbserver`：由 `JLinkGDBServerCLExe` 把 RTT channel 0 转发到 TCP

运行，不读 RTT。同一条 telnet 通道是双向的，参数下发也走它。

| 路径 | 覆盖率 | 最大间隔 |
| --- | ---: | ---: |


## 离线特征评估

采集后先用标记做一次特征筛选：

```sh
python3 tools/slip_analyze.py logs/slip_<时间戳> --sweep
```

它会输出每个候选特征在事件窗口内外的分布，并扫描阈值给出「命中事件数 / 误报数」。

**按键有反应延迟**：实测真实扰动峰值出现在按键**之前** 391–737 ms，所以工具默认用非对称窗口
`[标记 - 1.2 s, 标记 + 0.2 s]`。用对称窗口会把噪声当成事件。需要时用 `--lag-back` /
`--lag-fwd` 调整。

首次标注采集（`20261008_004933`，操作员确认只有 **4 次真实打滑**，其余全是误报）的结果：

| 特征 | 误报 max | 真值 min | 分离比 | 干净阈值 |
| --- | ---: | ---: | ---: | --- |
| `slip_metric` | 30.54 | 41.82 | 1.37x | (30.5, 41.8] → 36 |
| `\|d wheel speed/dt\|` | 1062 | 1477 | 1.39x | (1062, 1477] → 1270 |
| `\|wheelL-wheelR\|` | 59.30 | 71.55 | 1.21x | (59.3, 71.6] → 65 |
| `wheel_minus_body` | 3.95 | 5.22 | 1.32x | (3.95, 5.22] → 4.6 |
| `\|I_L-I_R\|` | 29810 | 25822 | 0.87x | **无法分离** |
| `\|torqueL-torqueR\|` | 11.03 | 8.65 | 0.78x | **无法分离** |
| `\|ax_lin\|` | 1.27 | 0.47 | 0.37x | **无法分离** |

**固件当前阈值偏低。** `VMC_BODY_MOTION_KF_SLIP_ACCEL_DEFAULT` 是 9.0，在这段 120 秒记录上产生
64 次触发，其中只有 23 次落在 4 个真实事件内；即使加上 60 ms 确认时间，仍有 11 次触发、3 次误报。
按本批数据，阈值应提高到 **36** 左右（配 10 ms 确认），可得到 8 个触发全部落在 4 个真实事件内、0 误报。

每次真实打滑在 `slip_metric` 上呈现**两个相隔约 100–120 ms 的短峰**（各 13–36 ms），推测是打滑瞬间
和恢复瞬间。

**样本量警告：只有 4 次打滑。** 上面的阈值和分离比来自单次记录，不能直接固化。需要每个工况重复
至少 10 次，再用留一法验证后才写进固件。

## 运行时切换打滑阈值

阈值不用重新烧录，采集脚本会随采集一起下发：

```sh
# 只测阈值，采集数据；门控不参与，记录的是原始 latch
python3 tools/slip_capture.py --duration 120 --mode both \
    --slip-threshold 36 --slip-confirm-ms 10 --label thr36

# 让门控真正生效，用于验证阈值对滤波器的影响
python3 tools/slip_capture.py --duration 120 --mode both \
    --slip-threshold 36 --slip-confirm-ms 10 --slip-gate --label thr36_gate
```

- `--slip-threshold` 映射到固件的 `slip_accel`（condition C 阈值）。
- `--slip-confirm-ms` 映射到 `slip_confirm_ms`（确认时间）。
- `--slip-gate` 决定 latch 是否真的去剔除卡尔曼的轮速输入。默认关闭，这样采集本身不会改变被测数据。
- 三个参数都不传时行为与之前完全一致；不传阈值就不下发 `slip_accel`，固件保持当前值。

`summary.json` 会同时记录请求值和从遥测读回的**实际生效值**（字段 `slip_requested` /
`slip_applied`），避免"以为改了实际没改"。

阈值可以逐个试而无需烧录：

```sh
for t in 20 25 30 36 45; do
  python3 tools/slip_capture.py --duration 60 --mode both \
      --slip-threshold "$t" --label "thr$t"
done
```

注意 `VMCVOFA` 字段 116/117（`kf_slip_left/right`）现在输出的是**原始 latch**，不受 `slip_enable`
影响，否则在默认采集模式下这两个字段会恒为 0，无法验证阈值。门控是否真的生效看字段 104
（`kf_slip`）。

## 阈值结论（2026-10-11，两轮共 219 秒 / 19 次打滑）

**固件编译默认值：`slip_accel = 33`，`slip_confirm_ms = 5`。**

> **2026-10-08 那版的 16 已作废。** 它是在 `dd_x`（condition C 里的机身加速度项）**还指向
> 侧向加速度计轴**的时候标定的。轴修复后固件算的指标已经不是当时那个量了，所以必须重标。
> 详见 `App/Inc/vmc_probe.h` 里 `VMC_BODY_MOTION_KF_SLIP_ACCEL_DEFAULT` 的注释。

依据两轮标注采集，均为 225 Hz 二进制 VMCFAST、两路 100% 覆盖：

| 采集 | 时长 | 标记次数 |
| --- | ---: | ---: |
| `logs/slip_20261011_012244` | 132 s | 10 |
| `logs/slip_20261011_012936` | 87 s | 9 |

阈值扫描（每个标记事件记一次命中）：

| 阈值 | 命中 | 额外检出 | 备注 |
| ---: | ---: | ---: | --- |
| 25 | 19/19 | 1 | 召回满，多 1 次误报 |
| **33** | **19/19** | **1** | **当前默认值** |
| 37 | 17/19 | 0 | 省下 1 次误报，但漏 2 次真实事件 |

另有两条独立验证：留一法 10/10；以及**完全不用事件窗口**直接数触发段，阈值 ≥25 时触发段与标记
事件一一对应。

**按键延迟比上一批大得多**：实测峰值滞后标记 **0.4–2.4 秒**（上一批是 0.39–0.74 秒）。用默认的
1.2 秒窗口会把 3 次真实峰值切到窗口外、并制造出一个假的高分位，从而得出"没有任何特征能区分"的
错误结论。窗口要开到 **`--lag-back 2500`**；实测 ≥2000 ms 后结论完全稳定，不依赖窗口精调。

**唯一那 1 次额外检出**：峰值 36.99，**高于最弱的已标记事件（35.76）**，所以靠阈值分不开。
区别在**持续时间**——它只有 5 ms（2 个采样点），最弱真实事件有 13 ms。没有用加大
`confirm_ms` 去滤它：可用间隔只有 10–13 ms，而 `confirm_ms` 是最快牺牲真实召回的参数。

## RTT 命令

### 打滑后的 LQR 权重切换（新增，默认关闭）

移植自南航哨兵轮腿固件（`开源参考/南航/SENTRY_LEG`）。那块代码在打滑时做两件事：

```c
Fitting_K[i][2] = Fitting_K[i][3] = 0;       // 清零 YAW 列
Fitting_K[i][4] *= 2;  Fitting_K[i][6] *= 2; // 加倍腿角列（两条腿）
```

**只有"加倍腿角"这一半被移植**，因为本固件的 LQR 状态是
`theta, dtheta, x, dx, phi, dphi` —— **没有 yaw 状态**，航向由独立的 `yaw_hold` 环单独保持。

```sh
# 打滑时把该侧腿角反馈 ×2（对应参考实现）
python3 tools/slip_capture.py --duration 120 --mode both \
    --slip-lqr on --label slip_lqr_on

# 对照：同动作、关掉
python3 tools/slip_capture.py --duration 120 --mode both \
    --slip-lqr off --label slip_lqr_off
```

- `--slip-lqr on|off` → `slip_lqr_enable`（固件默认 **1**，见下）
- `--slip-lqr-theta-scale` → 腿角缩放（默认 2.0，与参考一致）
- `--slip-lqr-dtheta-scale` → 腿角**速率**缩放（默认 1.0，即不缩放，与参考一致）
- `--slip-wheel-current-scale` → **最终轮电流**缩放（默认 0.6，与参考一致）

**关于速率项**：参考只放大位置项、不动速率项，那会把该环的阻尼比拉低约 `sqrt(2)`。如果打滑后
出现振荡，把 `--slip-lqr-dtheta-scale` 也提到 2.0 试 —— 所以它是独立参数而不是写死 1.0。

**遥测字段 151/152** 记录每侧**实际生效**的缩放值（1.0 = 未缩放）。这能区分"响应根本没触发"和
"触发了但输出上看不出来"。

缩放作用在**误差**上而不是增益上：`K` 数组每个周期都会被 `vmc_update_lqr_gain()` 重写，原地改
增益会被覆盖或累积。

#### 轮电流 ×0.6（参考响应的另一半）

同一个函数里参考还做：

```c
if (flag->slip_flag[i]) joint_m[i]->A = joint_m[i]->A * 0.6f;
```

作用在**最终电机电流**上（已限幅、已含 yaw）。本固件的对应点是
`vmc_balance_apply_wheel_output()` 里刚组装完的 `left/right_current`（= 平衡指令 + 手动 + yaw_hold
/ 云台跟随）。**遥测字段 153/154** 记录每侧实际生效的电流缩放。

**调之前先读这段** —— 这是参考响应里唯一"跟机器对着干"的一项：**轮电流就是轮腿平衡车的平衡
权限**。削掉 40% 等于交出 40% 抑制俯仰的能力，而且恰好在机器正在打滑、本来就受扰动的时候交。
参考机器也这么做，所以不是错误实现 —— 但它是**在另一台机器上最可能不划算**的一项，这也是它被
做成参数而不是常量、并且第一条要退的就是它的原因。

**要保留权重切换但不要削电流，把它设成 1.0。** 它由 `slip_lqr_enable` 总开关控制。

#### 默认值（2026-10-11，依据首次 on/off 对照）

`slip_lqr_enable` 已从默认 0 改为 **1**。依据那次对照（21 vs 23 次打滑，用不受开关影响的原始
latch 对齐，取触发后 200ms 窗口）：

| 指标 | OFF | ON | 比值 |
| --- | ---: | ---: | ---: |
| \|Δtheta\|（腿角扰动） | 0.372 | 0.289 | **0.78** |
| roll 峰峰值 | 0.040 | 0.028 | **0.70** |
| \|pitch\| 峰 | 0.202 | 0.204 | 1.01 |
| tp_cmd 峰 | 7.47 | 11.19 | 1.49 |

`tp_cmd` 峰值 31.8 / 限幅 108，**余量 71%，饱和 0 帧** —— 代价付得起。

**证据强度要说清**：只有两次采集、事件不同（ON 那次的轮速突变还更大，是**不利于** ON 的偏差），
配对检验 `P(ON<OFF) = 0.69~0.70`。所以"方向正确、量级温和"可信，"22%/30%"这种具体数字不可信。


关闭高频流：

```json

```

## 运行时切换接地跟随伸长 / roll 补偿

`leg_follow`（脱空侧追地面往外伸腿）和 roll 补偿一样可以在采集时下发参数，一次运行同时配置并记录：

```sh
# 整机模式：任意一侧脱空，两条腿一起伸长（默认）
python3 tools/slip_capture.py --duration 120 --mode both \
    --leg-follow on --leg-follow-machine-wide on --label follow_wide

# 单腿模式：只有脱空的那条腿伸，用于排查行驶中单轮被顶起
python3 tools/slip_capture.py --duration 120 --mode both \
    --leg-follow on --leg-follow-machine-wide off --label follow_perleg

# 关掉跟随做对照
python3 tools/slip_capture.py --duration 120 --mode both \
    --leg-follow off --label follow_off
```

- `--leg-follow on|off` → `leg_follow_enable`，跟随功能总开关。
- `--leg-follow-machine-wide on|off` → `leg_follow_machine_wide`，1=任意一侧脱空两条腿一起伸，0=只伸脱空那条。
  **仅在 `leg_follow_auto_scope=0` 时生效**，默认情况下范围是自动判的，见下。
- `--leg-follow-rate` → 脱空时向外追的速率（m/s，固件默认 `0.2`）。
- `--leg-follow-return-rate` → 重新接地后回落到预设的速率（m/s，固件默认 `0.05`）。
- 不传的键保持固件当前值，不会被动重置。`summary.json` 记录 `leg_follow_requested` 和从遥测读回的
  `leg_follow_applied`（左右两条腿的 offset）以便交叉核对。

**默认自动伸【低侧】那条腿**（`leg_follow_auto_scope = 1`）：一侧掉下平台和把一侧抬起来，动作
都是"伸低侧那一条"，理由和实测依据见 `docs/硬件配置.md`。低侧判定要持续
`leg_follow_scope_confirm_ms`（默认 250 ms）才被采信，然后锁住。要在采集里固定范围做对照实验，
得先下发 `leg_follow_auto_scope=0`。

schema 14 的采集里字段 143 记录**本次实际在伸哪条腿**、144 是否有脱空事件、145 判定是否已定、
146 正在计时中的候选侧，配合字段 122（`roll`）就能复盘每次判定，包括"某个瞬态被看到但没被
采信"；旧采集没有这些列。

**注意**：跟随由每侧接地 latch（`airborne_side_active_*`）触发，而该 latch 要求
`wheel_speed >= 阈值`。行驶/旋转场景轮子在转，能触发；纯用手慢慢抬、轮子不转时 latch 不会置位，
跟随也就不会启动。这类场景需要在固件里放开轮速条件后再采。

采集后用 roll 补偿 / 接地诊断看跟随是否真的伸长：

```sh
python3 tools/roll_comp_report.py logs/<stamp>/kalman_samples.csv
```

它除了 roll 补偿，还会在 schema 11 的采集里打印 "ground-following extension" 一节，给出左右
`leg_follow_offset` 的峰值和激活帧数；没有该列的旧采集会自动跳过这一节。

### 腿长下限是量出来的，不是猜的

`VMC_LEG_LENGTH_MIN` 原来是 `0.120`，**是错的**。实测证据：

```
slip_20261009_223938：目标连续 40 s 钉在 0.119 m，
                       实测左腿 0.161 m，波动只有 ±1 mm
```

目标动、腿不动、幅度只有毫米级 —— 这是顶到**机械限位**，不是控制器没力气。卷尺量出来最短腿长
就是 **0.160 m**。当前软件下限保留 `10 mm` 安全余量，`VMC_LEG_LENGTH_MIN`
设为 `0.170`，避免继续长期顶住机械限位。

顺带更正一个之前的误判：那 42 mm 的"跟随误差"（目标 0.119 / 实测 0.161）不是"PD + 恒定前馈的
稳态误差"，而是**撞限位**——`0.160 - 0.119 = 41 mm`，和实测 42 mm 基本一致。

### roll_comp_limit 的物理上限

`roll_comp_limit` 现在取软件行程极限 `VMC_ROLL_LENGTH_COMP_LIMIT_MAX = **0.1075 m**`，编译默认值
与它相同。补偿器对两条腿做对称偏移（`left = clamp(T + offset)`、`right = clamp(T - offset)`），
所以**永远不会被裁掉**的最大偏移是半个行程：

```
(VMC_LEG_LENGTH_MAX - VMC_LEG_LENGTH_MIN) / 2 = (0.385 - 0.170) / 2 = 0.1075 m
```

只有预设正好在行程中点（0.2775 m）时才拿得到。实际每个档位取**两侧余量里小的那个**，
注意它不总是收缩侧：

| 档位 | 预设 T | 收缩余量 | 伸长余量 | 对称上限 |
|---|---|---|---|---|
| SHORT | 0.170 | **0 mm** | 215 mm | **0 mm** |
| MID | 0.260 | 90 mm | 125 mm | **90 mm** |
| LONG | 0.360 | 190 mm | **25 mm** | **25 mm**（伸长侧先卡） |

**结论**：常量与软件行程极限一致时它不再是限制项，改由行程限制。SHORT 档正好位于软件下限，
收缩侧没有余量；LONG 档距离机械上限只剩 **25 mm**（`0.385 - 0.360`），伸长侧先受限。
平台工况下 roll 补偿能否压动平台侧那条腿，取决于当前档位对应的实际行程余量，
调 `roll_comp_limit` 救不了已经顶到机械边界的情况。

另外，两条腿是**各自独立** clamp 到 `[MIN, MAX]` 的：偏移一旦超过对称上限，收缩侧顶死、伸长侧
继续走，这一对就不再是纯力偶，而是同时把机身往上顶。`tools/roll_comp_report.py` 的
`CLIPPED` / `LIMIT CONTACT` 两行报的就是这件事。

配合 gain `0.4`，限幅现在要到 `0.1075 / 0.4 = 0.269 rad`（15.4°）才介入，此前是
`0.08 / 0.4 = 0.200 rad`（11.5°）。两个 clamp 位置（姿态环与 RTT 写入）共用
`VMC_ROLL_LENGTH_COMP_LIMIT_MAX`，`tools/test_roll_comp_limits.py` 会盯着 MIN、上限、
两个 clamp 点和各档余量表不走偏。

## 采集失败时的排查（"no RTT telemetry" / "listener port"）

采集启动会先检查 `2331`（GDB）和 `19021`（RTT telnet）能不能用。被占用时直接报出占用进程，
不会再出现"连上了但一条数据都没有"的超时。两类原因：

1. **IDE 调试会话占着探针**。Trae / VS Code 的 Cortex-Debug（或 Ozone）会自己拉一个
   `JLinkGDBServerCLExe`，和采集脚本抢同一个 J-Link 和同一个 RTT 端口。先结束那个调试会话。
2. **上一次采集残留的 server**。`GdbServerRttReader` 在 `wait_for_telemetry()` 超时时会清理自己
   拉起的进程；更早的版本不会，于是一次失败就把 `2331` 一直占住，后续每次采集都失败。

排查与清理：

```sh
# 谁占着端口
lsof -nP -iTCP:2331 -iTCP:19021 -sTCP:LISTEN

# 端口已释放、但仍有残留进程
ps aux | grep -iE "JLinkGDBServerCLExe|arm-none-eabi-gdb" | grep -v grep
kill <pid>          # 只杀 PPID=1 的孤儿进程，别动 IDE 正在用的那个
```

如果日志只有 J-Link 的 banner（`SEGGER J-Link ... Real time terminal output`）而没有任何
`VMCVOFA`/`VMCFAST`，说明 **CPU 没有在跑固件**（掉进 HardFault，或被调试器停住）。此时
`continue` 也救不回来，需要复位或重新烧录。烧录前照旧先卸载荷、跑
`tools/check_safe_to_flash.py`。

## 烧录安全

烧录会复位 MCU，所以**先卸掉腿的负载**（吊起、支撑好或已经躺下），再执行检查：

```sh
python3 tools/check_safe_to_flash.py
```

它采样 3 秒，满足以下**任一**条件就放行（退出码 0）：

1. **操作员已下达停止指令**。固件把全部关节和轮输出都串在
   `remote_control_allows_joint_enable()` 后面，该函数要求遥控有效、帧不超时、且新遥控通道 4
   不在上档急停位置。
   因此以下任一种情况都会把整条驱动链强制归零：
   - 通道 4 打回上档 `-1`（急停；遥测中 `remote_s1=2`）
   - 遥控不在线（`rc_source == 0`）

   该状态需在整个窗口内保持 ≥90%、且至少 20 帧，避免单帧误判。

2. **受门控的输出为 idle**（遥控状态读不到时的回退判据）。不要用 `*_tp_cmd` 或
   `*_wheel_torque_raw` 判断——它们是 LQR 需求值，控制器失能时照样每周期计算。

退出码：0 安全、1 控制器在运行、2 读不到遥测或**连不上 J-Link 探针**（两种都按不安全处理，
除非操作员明确确认已失能）。探针不可达时脚本打印 `CANNOT TELL` 并返回 2，不会抛异常回溯。

**新遥控映射**：遥测 `remote_s1` 由 SBUS 通道 4 合成，通道 4 上档急停时为 `2`；
`rc_source=3` 表示本地 SBUS 在线。若启动姿态校验失败，`rc_source` 会保持 0，控制不会使能。

如果脚本提示"输出仍在驱动，但通道 4 已急停或遥控已离线"，请停下来排查——这种组合按理不可能
出现，说明固件门控有问题。
